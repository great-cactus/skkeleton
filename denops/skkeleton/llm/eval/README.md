## 何を比べるか

| 機能           | 比べるもの                          | 正解の条件                         |
| -------------- | ----------------------------------- | ---------------------------------- |
| F2（並べ替え） | 辞書の 1 位 / LLM 補助を通した 1 位 | LLM 補助を通した 1 位が `expected` |
| F1（候補生成） | 文脈あり / 文脈なしで生成した候補   | 文脈ありの候補が `expected`        |

F2 は、実際の変換と同じ `llm/assist.ts` を通す。処理の順は次のとおり。

1. 読みの分割（主）：送りなし変換で辞書に候補があるとき、読みの末尾を送り仮名・助詞として切り分けて辞書を引き直し、候補を最大4件補う（`llm/split.ts`。例：ながい→長い、きょうか→今日か）
2. 並べ替え：辞書の先頭K件と分割の候補をzenzで採点する
3. 読みとの比較（予備）：読みそのものも採点し、辞書・分割のどの候補より高ければ、候補はどれも外れているとみなしてzenzに生成させ、先頭に置く

F2 の表には次の列も出る。

- `llm(前のみ)`：カーソル後の文脈を渡さない場合。文章の末尾で入力しているときは
  カーソル後に文がないので、実際の入力に近いのはこちら
- `llm+topic`：話題（topic 条件）を付けた場合。ケースに `topic` を書くか、
  要約器（`SKKELETON_TOPIC_ENDPOINT`）を指定したときだけ出る
- `route`：分割・予備の生成が働いたか（例：`分割+4`、`読み1位→生成:描いた`）
- `issue`：並べ替えでは正解に届かない理由
  - `候補外`：辞書・分割・生成のどれにも正解がない
  - `上位5件外`：正解が並べ替えの対象（先頭`llmRerankMaxCandidates`件）より後ろにある

分類ごとの集計には、辞書で不正解だったものを LLM が直した数（改善）と、
辞書で正解だったものを LLM が崩した数（改悪）も出る。

## ローカルでの実行手順

1. echo と logprobs に対応した llama-server で zenz-v3.2 系の GGUF を起動する

   ```sh
   llama-server -m zenz-v3.2-small-Q5_K_M.gguf --port 8080
   ```

2. （任意）話題の要約に使う、指示に従えるモデルを別のポートで起動する

3. 評価テストを実行する

   ```sh
   SKKELETON_ZENZ_ENDPOINT=http://127.0.0.1:8080 \
   SKKELETON_EVAL_JISYO=/path/to/SKK-JISYO.L \
   SKKELETON_TOPIC_ENDPOINT=http://127.0.0.1:8081 \
     deno test -A denops/skkeleton/llm/eval/
   ```

| 環境変数                                           | 必須 | 内容                                                                             |
| -------------------------------------------------- | ---- | -------------------------------------------------------------------------------- |
| `SKKELETON_ZENZ_ENDPOINT`                          | ○    | zenz サーバの URL。無いとテストは実行されない                                    |
| `SKKELETON_EVAL_JISYO`                             |      | SKK 辞書のパス。F2 の候補を辞書から読み直し、F1 の読みが辞書にないことを確かめる |
| `SKKELETON_EVAL_JISYO_ENCODING`                    |      | 辞書の文字コード（既定 `euc-jp`）                                                |
| `SKKELETON_EVAL_RERANK_K`                          |      | 並べ替える件数（既定5）。`5`と`10`で実行し、表の`ms`列で速さを比べる             |
| `SKKELETON_TOPIC_ENDPOINT` / `_MODEL` / `_API_KEY` |      | 話題の要約器（chat completions API）                                             |

## ケースの書き方（`cases.ts`）

- F2 は、同じ読みに対して文脈を変えた複数の文をまとめて書く（`F2Group`）。
  `candidates` は SKK-JISYO.L の順に、注釈を除いて書く
- 文脈は、変換済みの文がバッファにある状態を想定して漢字かな交じりで書く
- 分類
  - `homophone-sentence`：正解の手がかりが変換中の文の中にある
  - `homophone-document`：手がかりが主に前の文にある（話題で拾えるかを見る）
  - `dict-mismatch`：辞書に候補はあるが正解がない（送り仮名を区切らずに入力した用言、語の区切りの誤り）。分割と予備で正解を候補に入れられるかを見る。辞書全体が要るので、`SKKELETON_EVAL_JISYO`を指定しないときは実行しない
  - F1 `proper-noun`：前の文で定義された固有名詞。読みは辞書にない並び全体にする
  - F1の`okuri-missing`：送り仮名の区切りを入れずに入力した用言（読み全体で辞書を引くと0件になる）

## ケースを作る中で分かったこと

- **辞書に候補はあるが正解がない誤りがある**（「ながい」→永井・長井、「かいた」→海田、「きょうか」→強化など）。F2は辞書の候補を並べ替えるだけなので直せず、辞書に候補があるのでF1も動かない。これに対して読みの分割（主）と読みとの比較（予備）を入れ、`dict-mismatch`で評価する
- `dict-mismatch`の58件のうち53件は、分割で正解が候補に入る。残り5件（掻く・点く・経つ・蒔く・描いた）は分割の候補数の上限で入らないので、予備で拾えるかを見る
- **並べ替える件数が5件だと、正解に届かないケースが7件ある**（済み・対称・硬貨・気管・試行・嗜好・快方。辞書の6〜8番目）。10件にすると全ケースが対象に入る
